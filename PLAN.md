# Work Tracker — Implementation Spec

> **For the implementing model:** read this whole document before writing any code. It is the single source of truth. When something is not specified, choose the simplest option that fits the rest of the spec, and note the choice in `NOTES.md`. Do not add features, libraries or services that are not listed here.

## 0. Rules for the implementing model

1. **Build in phase order** (§13). Finish a phase and pass its checks before starting the next one.
2. **Stack is fixed:** Node.js 20 LTS or newer, plain JavaScript (ES modules, no TypeScript), Express 5, EJS 3, cookie-parser, exceljs. Tests use the built-in `node:test` runner. Do **not** add:
   - React, Vue, Svelte, Alpine, HTMX or any other front-end framework
   - Tailwind, Bootstrap or any other CSS framework, or chart libraries
   - a database (SQLite, Postgres, Prisma, Sequelize) or an ORM
   - TypeScript, a bundler (Vite, webpack, esbuild) or a build step
   - Docker, or any Python code
   Do not add any dependency that is not listed in §2.1 without writing the reason in `NOTES.md`.
3. **No external network assets.** No CDNs and no web fonts. Everything the browser loads comes from `app/public/`. The app must work fully offline and behind a corporate proxy.
4. **All git calls go through `app/git-sync.js`.** Never use `git add -A`, `git add .` or `git push --force`. Never commit anything outside `data/` (except the spec's own setup commits described in §13).
5. **All data access goes through `app/store.js`.** Routes never read or write files directly.
6. **Cross-platform.** All code must work on Windows and Linux:
   - Build paths with `path.join` / `path.resolve`. Never hard-code `/` or `\`.
   - Run external programs with `execFile` or `spawn` and an argument array. Never use `exec` (it takes a command string). The one exception is the npm call on Windows in §3.3.
7. **ES modules everywhere.** `package.json` has `"type": "module"`, so use `import`/`export` and `node:`-prefixed built-ins (`node:fs/promises`, `node:path`, `node:child_process`). Use `async`/`await`; do not use callbacks.
8. **JSDoc types** on every exported function. Keep functions short. Add a comment only where the behaviour is not obvious.
9. After each phase: run `npm test`, start the app with `./start.sh`, and click through the pages in that phase's checks.
10. **Keep `NOTES.md` up to date.** Before you finish any working session, add a progress entry (template in `NOTES.md` §4) and update the status table. Record any decision the spec does not cover in `NOTES.md` §2. The next session may run on a different device and will only see the repo, so anything not written in `NOTES.md` or `PLAN.md` is lost.

## 1. What we are building

A personal web app, used by one presales/solutions person at a time, for tracking RFQs/deals, customers and people. It runs locally in the browser at `http://127.0.0.1:8765`.

- **One command to start.** After `git clone`, run `./start.sh` (Linux/macOS) or `start.bat` (Windows). The script sets everything up and opens the browser.
- **The data lives in the repo.** Every record is one JSON file under `data/`.
- **Automatic versioning.** Every save becomes a git commit, and commits are pushed to the enterprise git remote automatically.
- **Multi-laptop.** The same repo can be used from a Windows laptop and a Linux machine. Data syncs through the remote.
- **Remote repository:** `https://github.com/amodmulay-ltts/ai-work-mgmt.git` (remote name `origin`, branch `main`). This repo holds both the code and the data.

**Out of scope:** user accounts and login, multi-user editing, C4C API integration or links (the C4C ID is plain text), currency conversion / FX rates, file attachments (store links only), a mobile layout, email sending, importing existing Excel data.

## 3. Launchers and bootstrap

All real logic lives in `run.js`. The shell scripts only check that Node is installed and hand over to it.

### 3.1 `start.sh` (use exactly this)
```sh
#!/usr/bin/env sh
cd "$(dirname "$0")" || exit 1
if ! command -v node >/dev/null 2>&1; then
  echo "Node.js 20 or newer is required. Install it from https://nodejs.org and run ./start.sh again."
  exit 1
fi
exec node run.js "$@"
```

### 3.2 `start.bat` (use exactly this)
```bat
@echo off
setlocal
cd /d "%~dp0"
where node >nul 2>nul
if errorlevel 1 (
  echo Node.js 20 or newer is required. Install the LTS version from https://nodejs.org and run start.bat again.
  pause
  exit /b 1
)
node run.js %*
set rc=%errorlevel%
if not "%rc%"=="0" pause
exit /b %rc%
```

### 3.3 `run.js` behaviour

`run.js` uses **only Node built-in modules** until the dependencies are installed. It must not `import` anything from `node_modules` before step 4.

1. **Version check:** if the major version in `process.versions.node` is below 20, print `Node.js 20+ required, found vX` and exit with code 1.
2. **Arguments** (`util.parseArgs`):
   - `--port <number>` (default 8765)
   - `--no-browser`
   - `--offline` (skip all git network operations)
3. **Git check:** run `git --version` with `execFile`. It must succeed and report 2.30 or newer. Otherwise print an error and exit 1.
4. **Dependencies:**
   1. `LOCK = ROOT/package-lock.json`, `HASH_FILE = ROOT/node_modules/.lock-hash`.
   2. Compute the SHA-256 of `LOCK`. If `node_modules` is missing, or `HASH_FILE` is missing or differs from the hash, print `Installing dependencies...` and run `npm ci`.
   3. Run npm with `spawnSync`, `stdio: 'inherit'` and `cwd: ROOT`:
      - on Windows: command `npm.cmd`, with `shell: true`. The arguments are constants, so this is safe.
      - elsewhere: command `npm`, with no shell.
   4. On success, write the hash to `HASH_FILE`. On failure print `Dependency install failed. If you are behind a proxy, set HTTPS_PROXY (or configure npm's proxy setting).` and exit 1.
   5. If `package-lock.json` does not exist (only during Phase 0), run `npm install` instead and print `Commit package-lock.json to the repo.`
5. **Git repo bootstrap:**
   - If `ROOT/.git` does not exist: run `git init -b main` and print a warning that no remote is configured.
   - If no `origin` remote is configured: print `No git remote configured. To enable sync run: git remote add origin https://github.com/amodmulay-ltts/ai-work-mgmt.git` and keep running.
   - If `git config --get user.name` or `user.email` is empty: ask for them with `readline/promises`, then store them with `git config user.name ...` (repo-local, not global).
6. **Start the app:** `const { createApp } = await import('./app/server.js')`. Then `const { app, store, git, startup } = await createApp({ root: ROOT, syncEnabled: !offline, startupPull: true })`. `createApp` pulls first (step 7), then initialises the store, then starts the push worker (§10).
7. **Startup pull** (unless `--offline` or there is no remote): `await git.pull({ interactive: true })`. This must run **before** the store creates `config.json`. Otherwise a second laptop would create its own default config and conflict with the one already on the remote. Interactive means git is allowed to prompt for credentials in the terminal the first time, so the normal stdin is used.
   - Print `Synced with remote` on success, or `Sync failed: <message> — continuing offline` on failure.
   - Never exit because of a sync failure.
   - If the pull changed files, call `store.loadAll()`.
8. **Choose a port:** try `--port` through `--port + 10`. For each, use `net.createServer().listen(p, '127.0.0.1')`; the first port that binds is used. Close the test server before using the port.
9. **Listen:** `const server = app.listen(port, '127.0.0.1', ...)`. Print `Work Tracker running at http://127.0.0.1:<port> — press Ctrl+C to stop`.
10. **Open the browser** (unless `--no-browser`), after the server is listening:
    - macOS: `open <url>`
    - Windows: `explorer.exe <url>`
    - other: `xdg-open <url>`
    Use `spawn` with `stdio: 'ignore'`, `detached: true`, and call `.unref()`. Ignore errors.
11. **Ctrl+C / SIGINT / SIGTERM:** the first signal runs `await git.flush(20000)`, then `server.close()`, then `process.exit(0)`. A second signal exits immediately with `process.exit(1)`.

### 3.4 Session lock (advisory, so two computers are not used at once)

**Purpose:** warn the user when another computer may be editing. It never blocks. Git still merges everything, so the lock only reduces conflicts.

- **File:** `data/_lock.json`, placed directly in `data/` (not in a kind folder), so `Store.loadAll` never reads it as a record. Content: `{ "holder": "<os user>@<hostname>", "started_at": "<nowIso()>" }`.
- **Holder identity:** `os.userInfo().username` + `@` + `os.hostname()`. The environment variable `WORK_TRACKER_HOLDER`, when set, replaces it. Tests use it to run two copies on one machine.
- **On start** (in `createApp`, after the startup pull and `store.init()`, before the server listens):
  1. Read `data/_lock.json`. If it exists and `holder` is not this session's holder, set `store.lockWarning` to `"<holder> has this open since <started_at>. Make sure it is closed before you edit, or changes may conflict."`. Otherwise `store.lockWarning` is `null`.
  2. Write the lock with this holder and `nowIso()`. Commit with `session: opened on <holder>` through `git.commitUnlocked`, then call `git.pushNow()` at once (do not wait for the 30 s delay), so other computers see the lock soon.
  3. `run.js` prints `store.lockWarning` in the terminal when it is set.
- **On clean shutdown** (`run.js`, before `git.flush()`): delete `data/_lock.json`, commit `session: closed on <holder>`, then flush. The commit and the flush happen in this order so the release is pushed.
- **Layout:** when `store.lockWarning` is set, `layout.ejs` shows it in a `.banner-warning` strip under the nav. It stays until the next start.
- **Stale locks:** a crash or a missing network leaves the lock in place. The next start on any computer shows the same warning. The app never refuses to start because of the lock.
- **Limits:** the lock is only as fresh as the last push from the other computer. Two computers with the same user name and hostname cannot be told apart.
- **Offline mode (`--offline`):** the lock is still written and committed locally, but nothing is pushed.

## 4. Domain rules

### 4.1 Stages (fixed defaults; stored in config and not editable in the UI)

| # | Stage | Default probability % | Terminal | Outcome |
|---|---|---|---|---|
| 1 | Lead | 5 | no | – |
| 2 | Qualified | 10 | no | – |
| 3 | RFI | 15 | no | – |
| 4 | RFQ Received | 25 | no | – |
| 5 | Solutioning | 35 | no | – |
| 6 | Proposal Submitted | 50 | no | – |
| 7 | Clarification / Negotiation | 70 | no | – |
| 8 | Won | 100 | yes | won |
| 9 | Lost | 0 | yes | lost |
| 10 | Dropped | 0 | yes | dropped |

### 4.2 Status (calculated, never stored)

- `stage` is terminal → status is `Won`, `Lost` or `Dropped`.
- Otherwise, if `on_hold` is true → status is `On Hold`.
- Otherwise → status is `Open`.

### 4.3 Automatic behaviours when a deal is saved

| Trigger | Effect |
|---|---|
| Stage changes | `probability` is set to the new stage's default. The user can still edit it afterwards. |
| Stage becomes `Proposal Submitted` and `submitted_on` is empty | `submitted_on = today` |
| Stage becomes terminal and `closed_on` is empty | `closed_on = today` |
| Stage moves from terminal back to non-terminal | `closed_on = None` and `outcome_reason = None` |
| New deal and `presales_owner` is empty | Defaults to `config.me_person_id` |
| New deal and `received_on` is empty | `received_on = today` |

### 4.4 Validation (show the errors on the form and keep the user's input)

- **Required:** `title`, `customer`, `type`, `stage`, `received_on`.
- **Date order:** `submission_due` must be ≥ `received_on` when both are set, and the same applies to `qa_due`.
- **Lost/Dropped:** `outcome_reason` is required when the stage is `Lost` or `Dropped`.
- **Ranges:**
  - `probability` is an integer from 0 to 100.
  - `est_value`, `effort_person_months` and `duration_months` must be ≥ 0 when set.
- **Links:** each URL must start with `http://` or `https://`.
- **Duplicate C4C ID:** if another deal has the same `c4c_id` (case-insensitive, trimmed), **save anyway** but show a warning: `Warning: C4C ID 1234 is also used by DL-2026-0003`.

### 4.5 Auto-create people and customers (so you can start from an empty system)

Owner fields and the customer field on the deal form are text inputs backed by a `<datalist>` of existing names. On save:

- **Customer field:** match the trimmed, case-insensitive name against existing customers. If nothing matches, create a new `Customer` with that name. Store `customer_id` on the deal.
- **Sales / Presales / Delivery owner:** match against existing people. If nothing matches, create a `Person` with role `Sales`, `Presales` or `Delivery` to match the field.
- **Customer contacts:** a textarea with one name per line. Each name is matched against people with role `Customer`. If nothing matches, create a person with `role="Customer"` and `customer_id` set to the deal's customer.
- **Commits:** auto-created records are written and committed in the **same commit** as the deal (§6.3: `commit(paths=[...all files...], message)`).
- **Flash message:** append the created names, e.g. `Saved · created customer "Bosch", person "Ravi K"`.

### 4.6 IDs

| Entity | Format | Example |
|---|---|---|
| Deal | `DL-{YYYY}-{NNNN}` (YYYY = year of creation, counter per year) | `DL-2026-0014` |
| Customer | `CU-{NNNN}` | `CU-0003` |
| Person | `PE-{NNNN}` | `PE-0021` |

- **Next number:** 1 + the highest existing number for that prefix, found by scanning filenames.
- **Before creating** a deal, customer or person, call `GitSync.pull()` (non-interactive, best effort, ignore failures). This avoids ID collisions between laptops. If a collision still happens, conflict handling (§6.4) preserves both versions.

## 5. Data model

### 5.1 `app/models.js`

Plain JavaScript with JSDoc typedefs. There are no runtime classes. A record is a plain object whose keys are written in the order below, which keeps the JSON files stable.

**Important:** dates are stored as `YYYY-MM-DD` **strings**, never as `Date` objects. Timestamps are ISO-8601 strings with the local offset (see `nowIso()` below).

```js

 *   updated_at: string

 *   role: Role,

  /** @param {string[]} errors */
  constructor(errors) { super(errors.join('; ')); this.errors = errors; }

 * @param {object} obj
 * @param {object} config  the merged config (for enum lists)
 * @returns {string[]}
 */
export function validateRecord(kind, obj, config) { /* see rules below */ }
```

**`validateRecord` rules:**
- A required field is missing or empty: error `"<field> is required"`.
- An enum value is not in its allowed list (§5.1 comments, and config lists): error `"<field>: unknown value '<value>'"`.
- `probability` must be an integer from 0 to 100. Numeric amounts must be ≥ 0 when set.
- A date must match `/^\d{4}-\d{2}-\d{2}$/` **and** be a real calendar date. Check it by round-tripping through `Date.UTC`.
- A link URL must start with `http://` or `https://`.
- `store.save()` calls `validateRecord` before writing and throws `ValidationError` if the list is not empty.

### 5.2 File format rules

- **One record per file:** `data/<folder>/<id>.json`.
- **Serialise with** `JSON.stringify(obj, null, 2) + "\n"`. Build the object in the typedef key order so diffs stay stable.
- **Encoding:** always read and write UTF-8 (`'utf8'`, given explicitly). Write LF newlines (`\n`).
- **Atomic writes:** write to `<file>.tmp` in the same folder, then `await fs.rename(tmp, final)`. On Windows, `fs.rename` replaces an existing file.
- **Timestamps:** `nowIso()` from `app/models.js` (local time, seconds precision, with offset).

## 6. Git sync (`app/git-sync.js`)

### 6.1 Class

```js
export class GitSync {
  /** @param {{ root: string, enabled?: boolean, pushDelaySeconds?: number, mutex: Mutex }} opts */
  constructor(opts) {}
  hasRemote()                                  // `git remote get-url origin` exits 0
  branch()                                     // `git rev-parse --abbrev-ref HEAD`; null if "HEAD" (detached)
  commit(paths, message)                       // -> Promise<boolean> (true if a commit was made)
  pull({ interactive = false } = {})           // -> Promise<PullResult>; fetch + merge + conflict handling
  schedulePush()                               // (re)arm the push timer
  pushNow()                                    // -> Promise<boolean>
  startWorker()                                // starts the background push loop (a single setTimeout chain)
  flush(timeoutMs = 20000)                     // final push on shutdown
  status()                                     // -> Promise<SyncStatus>, for the UI badge
}

/** @typedef {{ ok: boolean, changed: boolean, conflicts: string[], error: string | null }} PullResult */
/** @typedef {{ state: 'synced'|'pending'|'error'|'local'|'offline', unpushed: number, lastError: string | null, lastPushAt: string | null }} SyncStatus */
```

### 6.2 Running git and locking

- **Single helper:** `git(args, { interactive = false, timeoutMs = 60000 })`. It calls `execFile('git', args, { cwd: root, encoding: 'utf8', windowsHide: true, timeout: timeoutMs, env })`, wrapped in a promise. It **resolves** (never rejects) with `{ ok, code, stdout, stderr }`.
- **Environment:** when `interactive` is false, set `GIT_TERMINAL_PROMPT=0` so git can never hang waiting for credentials. Git Credential Manager on Windows may still show its own window, which is fine.
- **Locking:** `app/mutex.js` exports:
  ```js
  export class Mutex {
    #tail = Promise.resolve();
    /** @template T @param {() => Promise<T>} fn @returns {Promise<T>} */
    run(fn) { const r = this.#tail.then(fn); this.#tail = r.catch(() => {}); return r; }
  }
  ```
  Every public `GitSync` method and every `Store` write runs inside `mutex.run(...)`. A method that is already inside the lock and calls another method must call the **unlocked** internal version (for example `pullUnlocked()`), or it will deadlock.

### 6.3 `commit(paths, message)`

1. Every path must be inside `data/`. Otherwise throw `new Error('refusing to commit outside data/')`.
2. `git add -- <paths...>`. This also stages deletions of files that were removed.
3. If `git diff --cached --quiet -- <paths...>` exits 0, nothing changed: return false.
4. `git commit -m <message> -- <paths...>`. The pathspec makes sure only these files are committed, even if other files are staged.
5. Call `schedulePush()` and return true.

**Commit message formats:**

| Event | Message |
|---|---|
| Create | `DL-2026-0014: created – ADAS validation services – Phase 2` |
| Stage change | `DL-2026-0014: stage Solutioning → Proposal Submitted` |
| Edit of one field | `DL-2026-0014: submission due 2026-10-20 → 2026-10-24` |
| Edit of several fields | `DL-2026-0014: updated 3 fields` |
| Note | `DL-2026-0014: note added` |
| Delete | `DL-2026-0014: deleted` |
| Customer / person changes | `CU-0003: created – Bosch`, `PE-0002: updated` |
| Config | `config: updated settings` |
| Sync merge | `sync: merge remote changes` (`sync: merge remote changes (2 conflicts saved)` when there were conflicts) |

### 6.4 `pull()`: fetch, merge, conflict handling

```
if !enabled or !hasRemote(): return { ok: true, changed: false, conflicts: [], error: null }
b = branch(); if b is null: return error "Detached HEAD – checkout a branch"
git fetch origin                                        (fails -> return ok:false, error = stderr first line)
if `git rev-parse --verify origin/<b>` fails:           (remote branch doesn't exist yet, e.g. empty repo)
    return ok:true, changed:false
old = git rev-parse HEAD
git merge --no-edit --autostash origin/<b>
if merge succeeded:
    changed = (git rev-parse HEAD) != old
    return ok:true, changed
# merge has conflicts
conflicted = `git diff --name-only --diff-filter=U`
if any path does not start with "data/":
    git merge --abort
    return ok:false, error = "Code conflict in <paths> – resolve manually with git"
for path in conflicted:
    theirs = `git show :3:<path>`           (fails if the remote deleted the file)
    oursExists = `git cat-file -e :2:<path>` succeeds
    if theirs succeeded:
        write theirs to data/_conflicts/<stem>.<YYYYMMDD-HHMMSS>.theirs.json
    if oursExists: git checkout --ours -- <path>
    else:          git checkout --theirs -- <path>      (we deleted it, they edited it -> keep theirs)
    git add -- <path>
git add -- data/_conflicts
git commit --no-edit -m "sync: merge remote changes (N conflicts saved)"
return ok:true, changed:true, conflicts: [...]
```

- After any pull with `changed: true`, the caller must call `store.loadAll()`.
- "Ours" means the local version. **The local version always wins in the file.** The remote version is never lost, because it goes to `data/_conflicts/`.

### 6.5 Push worker

- `schedulePush()` sets `this.deadline = Date.now() + pushDelaySeconds * 1000` and, if no timer is running, starts one with `setTimeout`.
- **Worker** (`startWorker()`): a single `setTimeout` chain. When it fires, it checks the deadline. If the deadline has passed, it calls `pushNow()`. Otherwise it re-arms for the remaining time. The timer is `unref()`ed so it never keeps the process alive by itself.
- **`pushNow()`** (runs inside the mutex):
  1. If the remote branch is missing, or the branch has no upstream, run `git push -u origin HEAD`. Otherwise run `git push origin HEAD`.
  2. If the push is rejected (stderr contains `rejected`, `non-fast-forward` or `fetch first`): run `pullUnlocked()`, then retry the push once.
  3. **On success:** `lastError = null`, `lastPushAt = nowIso()`.
  4. **On failure:** store `lastError`, and retry with backoff: 30 s, 60 s, 120 s, 300 s, then 600 s at most. Never throw.
- **Unpushed count:** `git rev-list --count origin/<b>..HEAD`, or `git rev-list --count HEAD` if the remote branch does not exist.
- **`flush(timeoutMs)`:** if `unpushed > 0`, `await Promise.race([pushNow(), timeout])`. Called on shutdown (§3.3 step 11).
- **Status mapping** (checked in this order):
  - `offline`: sync disabled via `--offline`
  - `local`: no remote configured
  - `error`: `lastError` is set
  - `pending`: `unpushed > 0`
  - `synced`: otherwise

## 7. Store (`app/store.js`)

```js
export class Store {
  /** @param {{ root: string, git: GitSync, mutex: Mutex }} opts  root = repo root; data dir = root/data */
  constructor(opts) {}
  init()                              // create data dirs; write DEFAULT_CONFIG and commit it if config.json is missing; then loadAll()
  loadAll()                           // read all deals, customers, people and config into memory
  problems                            // string[]: files that failed to parse or validate. Shown as a banner, never crash.
  config()                            // DEFAULT_CONFIG overlaid with the file contents (missing keys get defaults)
  saveConfig(cfg, message = 'config: updated settings')
  nextId(kind)                        // 'deal' | 'customer' | 'person' -> 'DL-2026-0014', 'CU-0003', 'PE-0021'
  listDeals(), getDeal(id)            // getDeal returns null when not found
  listCustomers(), getCustomer(id)
  listPeople(), getPerson(id)
  findCustomerByName(name)            // trimmed, case-insensitive; null if none
  findPersonByName(name)
  stageNames(), stage(name)           // stage(name) returns the stage object from config
  save(records, message)              // validates and writes ALL records, then ONE commit
  delete(record, message)
}
```

- **`save()`:** inside `mutex.run`, for each record:
  1. set `updated_at = nowIso()`
  2. `validateRecord(kind, record, config)`. If there are errors, throw `ValidationError` **before writing anything**.
  3. write it atomically (§5.2)
  4. update the in-memory map

  Then call `git.commitUnlocked([all written paths], message)`. The lock is already held here, so calling the locking `commit()` would deadlock.
- **`delete()`:**
  - Removes the file and commits the removal.
  - Refuses to delete a **customer** that has deals: throw `Error("Customer has N deals")`.
  - Refuses to delete a **person** referenced by any deal or customer: throw `Error`. The UI offers "Mark inactive" instead.
- **`nextId(kind)`:** scan the filenames in the folder for the prefix. Next number = highest + 1, padded to 4 digits. Deals use a separate counter per year: `DL-<year>-NNNN`.
- **Loading:** ignore `data/_conflicts/` and any `*.tmp` file. A file that fails to parse or validate is added to `problems` and skipped.
- **Reloading** after a pull means calling `loadAll()` again. All maps are rebuilt from disk.

## 8. Metrics (`app/metrics.js`; pure functions, fully unit-tested)

All functions take `today` as a `YYYY-MM-DD` string parameter (never read the clock inside), which makes them testable. For day arithmetic, parse with `Date.UTC(y, m - 1, d)` and divide the difference by 86400000, so timezones cannot shift the result.

| Function | Definition |
|---|---|
| `status(deal, cfg)` | §4.2 |
| `is_open(deal, cfg)` | stage not terminal (on-hold deals count as open) |
| `age_days(deal, today)` | `(closed_on or today) - received_on`, in days |
| `days_in_stage(deal, today)` | `today - date of last history entry with kind=="stage"` (or `created_at.date()` if there is none) |
| `days_to_submission(deal, today)` | `submission_due - today` if `submission_due` is set and `submitted_on` is None; else None. A negative value means overdue. |
| `is_stale(deal, cfg, today)` | open, not on hold, and `today - updated_at.date() > cfg.stale_after_days` |
| `weighted_value(deal)` | `est_value * probability / 100`, in the deal's own currency (None if there is no value) |
| `aging_bucket(deal, today)` | `"0–30"`, `"31–60"`, `"61–90"` or `"90+"` from `age_days` |
| `health(deal, cfg, today)` → `{ level, reasons }` | see below |

**Health levels:**

- **Not open** → `("closed", [])`.
- **On hold** → `("hold", ["On hold"])`.
- **`red`** if any of these:
  - the submission is overdue: `"Submission overdue by Nd"`
  - `next_action_due` is more than 3 days in the past: `"Next action overdue by Nd"`
  - the deal is stale: `"No activity for Nd"`
- **`amber`** if any of these:
  - submission is due in 0–3 days: `"Submission due in Nd"` (or `"Submission due today"`)
  - `next_action_due` is today or in the past (0–3 days ago): `"Next action due"`
  - `next_action` is empty: `"No next action"`
- **`green`** otherwise, with no reasons.
- Collect **all** reasons that apply. The level is the most severe one.

**Dashboard aggregates:**

- **Money totals:** `moneyTotals(pairs, cfg)`, where `pairs` is `[currency, amount | null][]`, returns `{ [currency]: amount }` and sums the amounts **per currency** and skips None values. Keys are ordered by `config.currencies`; unknown currencies go last, alphabetically. Templates render the result with the helper `moneyTotals` (in `app/lib/format.js`) as `EUR 1.2M · USD 3.0M`, or `—` when it is empty. **Never add amounts in different currencies together.**
- `pipeline_by_stage(deals, cfg)`: for each non-terminal stage, the `count` and `totals` (= `moneyTotals` of `est_value`) of open deals. Bar widths are based on `count`.
- `aging_counts(deals, today)`: counts per bucket for open deals.
- `win_stats(deals, today, days=90)`: won and lost counts among deals with `closed_on` in the last 90 days. `win_rate = won / (won + lost)`, or None if both are 0.

## 15. Feature: RFQs I support

**Goal:** the user often supports RFQs that other people own (a colleague's sales deal, or another presales person's bid). Today the app only tracks the owner, so support work is invisible. This feature lets the user record "I support this RFQ", list the asks made of them, and see what they owe and when.

**Terms used here:**
- **Supporter:** a person in `Deal.support_ids`. Usually `role: 'Presales'`, but any active person is allowed.
- **Support request (ask):** one thing a supporter has been asked to do on a deal, such as "technical answers for Q&A", "effort estimate", "architecture slide". Asks are stored inside the deal file.
- **"My RFQs"** means deals where `me_person_id` is in `support_ids`, or where any open ask is assigned to `me_person_id`.

### 15.1 Data model changes (`app/models.js`, `app/config-defaults.js`)

Add two fields to `Deal`, placed right after `delivery_owner_id` so the key order stays stable:

```js
/**
 * @typedef {{
 *   id: string,                                  // SR-NNN, unique within the deal (e.g. SR-001)
 *   text: string,                                // what is needed, one line
 *   assignee_id: string | null,                  // a Person (any role); null = unassigned
 *   requested_by_id: string | null,              // a Person; null when unknown
 *   due_on: string | null,                       // YYYY-MM-DD
 *   status: 'Open' | 'In progress' | 'Done' | 'Cancelled',
 *   done_on: string | null,                      // set automatically when status becomes Done
 *   created_at: string,
 *   updated_at: string
 * }} SupportRequest
 *
 * // inside Deal, after delivery_owner_id:
 * //   support_ids: string[],                     // Person ids; no duplicates; the owner ids are not repeated here
 * //   support_requests: SupportRequest[],        // in the order created
 */
```

**Rules:**
- A new deal has `support_ids: []` and `support_requests: []`.
- `validateRecord('deal', …)`: each `support_ids` entry must be a known person id (checked in the store, not in `validateRecord`, same as other references). `support_requests[].status` must be one of the four values. `due_on` must be a valid date when set. `text` is required.
- Support request ids are `SR-001`, `SR-002`, … per deal. The next id is one more than the highest existing number in that deal (gaps are not reused).
- `done_on` is set to today when `status` changes to `Done` and cleared when it changes away from `Done`. The same rule as `submitted_on` in §4.3.
- Cancelled and Done asks do not count as open.
- Every add, edit, status change and removal of an ask appends one `HistoryEntry` to the deal (kind `field`, text such as "Ask SR-002 Done: Effort estimate").
- No config change is needed. The status list is fixed in the model, as `GO_NO_GO` is.

### 15.2 Metrics (`app/metrics.js`, pure, unit-tested)

- `openAsks(deal)` returns asks with status `Open` or `In progress`.
- `asksFor(deals, personId)` returns `[{ deal, ask }]` for every open ask whose `assignee_id` is `personId`, sorted by `due_on` (nulls last), then by deal id.
- `isSupportedBy(deal, personId)` is true when `support_ids` contains `personId`, or any open ask is assigned to `personId`.
- `nextAskDue(deal)` is the earliest `due_on` among open asks, or null.
- `askOverdue(ask, today)` is true when `due_on < today` and the status is open.

### 15.3 Routes and pages (`app/routes.js`)

| Method | Path | Purpose |
|---|---|---|
| GET | `/support` | **RFQs I support.** Lists deals where `isSupportedBy(deal, me)` is true. Filters: `q`, `status` (default `open`, same values as §10), `who` (`me` default, or any person id, to see a colleague's supported RFQs). |

### 15.6 Tests (`tests/support.test.js`)

- Adding a supporter that is not a person id is rejected.
- Adding an ask gives `SR-001`, and the next ask gives `SR-002`. After one is removed, the next ask is still `SR-003`, not a reused number.
- Marking an ask Done sets `done_on` to today. Changing it back to Open clears `done_on`.
- `asksFor` excludes Done and Cancelled asks, and sorts overdue asks first.
- `isSupportedBy` is true for a supporter and for an assignee, and false for others.
- `/support` shows a deal the user supports and hides a deal they do not.
- Each save makes exactly one commit and adds a history entry.

### 15.8 Decisions and open questions

- **Decided:** asks live inside the deal file, not in a separate folder, so one deal is one file and one commit (the same reason the history is inside the deal).
- **Decided:** a supporter is a person, not free text, so names match the people list and the customer/person auto-create rules still work.
- **Open (answer before S1):** should the user log effort hours per supported RFQ, for a "time on support" total? This is not in S1–S3. If yes, add `hours` to `SupportRequest` in a later phase.
- **Open (answer before S2):** should the **Support** nav item replace **Deals** for the user, or sit beside it? The spec assumes beside it.
